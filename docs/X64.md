# x86-64 backend

Flapjack can compile Pancake to little-endian x86-64, using CakeML's `x64`
target.  The backend reuses the whole Pancake-to-labLang compiler at word width
64 and adds an x86-64 assembler target.

This is a **parity-first** port.  Source-to-assembly output is checked
byte-for-byte against the original CakeML compiler.  The machine model and the
`encoderCorrect x64Target` obligation are described below; the full
Pancake-to-machine-code theorem is instantiated at the closed model when that
obligation is discharged.

## Code generation

- `Flapjack/Compiler/Encoders/X64/Encode.lean` ports the parts of the
  L3-generated `x64$encode` (`HOL/examples/l3-machine-code/x64/model/x64Script.sml`)
  that CakeML's `x64_ast` emits: the immediate helpers, `e_ModRM` (including
  SIB bytes for RSP/R12 bases and RIP-relative addressing), `rex_prefix`,
  `e_opsize`, `e_opsize_imm`, `e_opc`, `e_gen_rm_reg`, `e_rm_imm`,
  `e_rm_imm8`, `e_rax_imm`, and the SSE encodings used by the backend.
- `Flapjack/Compiler/Encoders/X64/Target.lean` ports `x64_ast`, `x64_encode`
  and `x64_enc`, restricted to the emitted instruction forms.  Conditional
  jumps follow `x64_encode`: `Z_ALWAYS` is always a rel32 `E9` branch, `Z_P`
  keeps the L3 short-branch choice (`7A rel8`), and every other condition is a
  rel32 `0F 8x` branch.
- `Flapjack/Compiler/Encoders/X64/Target.lean` also contains `x64_config`:
  16 registers, avoid registers 4 (RSP) and 5 (RBP), no link register,
  `two_reg_arith`, eight FP registers, `code_alignment := 0`, and CakeML's
  address, hardware, byte, jump, conditional-jump and `Loc` bounds.
- `Flapjack/Compiler/Backend/X64Config/` contains `x64_names` and
  `pancakeX64BackendConfig`, mirroring the ARM8 and MIPS32 configuration
  modules.

## Command-line use

`flapjack-compile --target=x64 SOURCE.pnk` emits a GNU x86-64 assembly file in
CakeML's `x64_export` frame: the preprocessor preamble, the `cml_main` startup
code, FFI stubs, `cake_clear`/`cake_exit`, the code-buffer markers, the
`makesym` lines, and the Windows calling-convention compatibility block.
`--hex` and `--sections` use the same compiled tuple.  The startup convention
is `ret = F`, `pk = T`, matching CakeML's Pancake x86-64 export.

## Parity evidence

`Flapjack/Test/X64Parity.lean` compiles the sources under `scripts/x64/parity/`
and compares both the whole assembly text and the code-byte hex with captured
original output:

```sh
cakeml/developers/bin/cake --pancake --target=x64 < case.pnk > case.cake.S
```

The checked-in `.cake.S` and `.cake.hex` fixtures let `lake test` run without a
local CakeML binary.  `scripts/x64/check-parity.py` regenerates or re-checks the
fixtures when the original compiler is available.  `scripts/x64/fuzz.py`
differential-tests randomly generated Pancake programs against the original
compiler; during development 1500 random programs and every standalone program
embedded in `cakeml/pancake/**/*.sml` that the original accepts matched
byte-for-byte.

## Machine model and theorem status

The closed x86-64 machine model lives under
`Flapjack/Compiler/Encoders/X64/Machine/`.  It decodes and executes the
instruction forms the backend emits.  This is **not** a port of CakeML's full
L3 x86-64 model: the L3 decoder accepts far more encodings than the backend
emits, and the closed model deliberately rejects everything else.

Current state of the proof work:

- `State.lean`, `Decode.lean`, `Execute.lean` and `Target.lean` define the
  model and the `x64Target` record.
- `Bytes.lean` proves the byte-level facts the decoder inverses need
  (`parseRM` layouts, little-endian immediate read-back, signed-width
  truncation).
- `Agree.lean` proves that equal projections are exactly agreeing states.
- `DecodeProof.lean` proves the decoder inverse for the register-only forms
  (`nop`, `cmc`, register moves, `jmp`, `setcc`, `monop .z64`, `mul .z64`,
  `div .z64`, register-register arithmetic and shifts) and for the immediate
  moves (`movRI .z32`/`.z64`).
- `EncodingProof.lean` proves that `jump`, `call` and `Loc` have
  offset-independent encoded lengths under `asm_ok`, and that a long
  conditional branch is six bytes.
- `TargetProof.lean` proves the `binopRR`/`binopRI`/`jumpCmp` encoded lengths,
  assembles them into `encOk x64Config`, and proves the projection-consistency
  half of `target_ok`; together these give `targetOk x64Target`.
- `MemDecodeProof.lean` records the encoded byte layout of `movRM .z64`.

**Not yet proved:** the decoder inverses for the memory-operand forms
(`movRM`, `movMR`, `movzxRM`, `lea`), the remaining immediate arithmetic forms
(`binopRI`), conditional jumps and the SSE forms; the execution-agreement
lemmas (`execInsn` versus `asmUpd`); the simulation framework and its
per-instruction cases; and therefore `encoderCorrect x64Target` and the
`panToTargetCompileSemanticsX64` instantiation.  `targetOk x64Target` is
proved, so `encoderCorrect x64Target` is missing only the transition
simulation.  No `@[hol]` tag is claimed for any declaration in the machine
model, and no `reviewed_*` row for it is present in
`docs/HOL-THEOREM-MAP.json`.

See `docs/SOUNDNESS.md` for the assurance limits of the closed model.
